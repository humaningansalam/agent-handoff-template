# v0.14.2 one-time adopter transition (Rollout Main)

This is a **procedure for one deliberately selected adopter** after its owner's review. It has not been run against the 30 consumers. Do not apply to unrelated repositories, do not run on TabletAuto, and do not copy this control-plane template's PRD into an adopter-owned product. Review existing dirty files, Task status and product documentation before edits.

## 1. Verify a pinned source and protect adopter state

Use the published **v0.14.2** archive `agent-workspace-control-plane-0.14.2.tar.gz`; check its SHA-256 against its release page before extraction. Extract to a separate directory, not over the current workspace. Save a deliberate Git commit/backup for adopter-owned root documents and Task/Knowledge records, including ignored `.repoctl-state` receipts and manifests. Preserve original product repositories, dirty baselines and completion history.

```bash
SOURCE=/absolute/path/to/agent-workspace-control-plane-0.14.2
./scripts/repoctl repo list --json
./scripts/repoctl task audit --include-archived --json
./scripts/repoctl upgrade plan --from "$SOURCE" --output .repoctl-state/upgrade-v0.14.2-plan.json --json
# Review the plan's replace/create/remove operations; do not apply blindly.
./scripts/repoctl upgrade apply --plan-file .repoctl-state/upgrade-v0.14.2-plan.json --json
./scripts/repoctl upgrade postflight --json
```

If the **read-only upgrade plan** finds an `archive_locator_migration_conflict`, stop without applying and have the adopter owner resolve the missing predecessor Task/archive identity from real evidence; never synthesize a replacement archive or rewrite a receipt. Hither and HostSpan currently have this blocker (28 of 30 non-TabletAuto adopter plans were conflict-free in the source audit). If postflight finds an archived/closed-task receipt conflict, halt rather than rewriting the receipt to today's hash.

## 2. Explicitly clean known Task-generated slop

```bash
./scripts/repoctl task migrate-slop --include-archived --json
./scripts/repoctl task migrate-slop --apply --json
# For each individually reviewed done, canceled or archived Task:
./scripts/repoctl task migrate-slop T-YYYYMMDDHHMMSSZ --closed --json
./scripts/repoctl task migrate-slop T-YYYYMMDDHHMMSSZ --closed --apply --json
./scripts/repoctl task doctor T-YYYYMMDDHHMMSSZ --json
```

Default apply **never** edits a done/canceled child just because it remains in `docs/tasks/`. One explicit `--closed` Task ID preserves its completion-time bytes in an ignored migration witness and checks the original receipt; receipt/catalogue hashes are not re-sealed. Do not run `--closed --apply` on a Task whose original proof is already mismatched. A proof is not new test/finish evidence. Inspect the precise Execution Log changes, including code fences and authored notes.

## 3. Convert Knowledge v1 only with real provenance

```bash
./scripts/repoctl knowledge migrate --repo-id main --json
# For each verified v1 ID with an existing technical reason and original source:
./scripts/repoctl knowledge migrate --repo-id main --record-id K-... --json
./scripts/repoctl knowledge migrate --repo-id main --record-id K-... --apply --json
# If the original lacks actual reason/source, supply verified input for that one ID:
./scripts/repoctl knowledge migrate --repo-id main --record-id K-... --reason 'Actual observed technical reason' --source docs/specs/example/requirements.md --apply --json
./scripts/repoctl knowledge check --repo-id main --json
./scripts/repoctl knowledge rebuild --repo-id main --json
```

Replace `main` with the repository ID shown by `repo list`. One-record apply prevents partial batch commits. **Do not overwrite or delete a v1 original**: this release preserves its exact path and bytes because current v2 records may cite its original SHA-256. A separate v2 record (or exactly equivalent current one) and an ignored digest-verified witness mark the conversion, and `knowledge check` excludes only proof-verified historical originals from repeated migration warnings. Missing reasons/sources must not be invented; changed source digests need explicit informed review. An invalid preservation witness restores a migration warning and requires investigation; do not delete it merely to pass postflight.

An existing current v2 that already cites the exact original v1 by SHA-256 and has the same claim/kind/repository can be attached via one explicit `knowledge migrate --record-id ID --apply`. `link_cited_current_v2` requires a unique, validated successor; it never changes the original v1 or current v2. When the current record narrows the historical file scope, review `removed_historical_scope_paths` before interpreting the current claim. New/broadened applicability, ambiguous successor records or tampered proofs are not auto-accepted. Old Task digest drift is **still visible** in current Knowledge checks after migration and must be reviewed separately.

For any `needs_source_review` result, inspect the actual old digest, current source, product applicability and original Task/receipt identity before providing explicit override flags. Do not treat missing product files, abandoned source paths or moved documentation as proof of a current invariant. Older v2 records referencing a v1 file must retain valid original-source hashes after migration.

## 4. Migrate old project documents and references

The current root entrypoint is `docs/PRD.md` and the optional current paths are `docs/architecture/`, `docs/specs/<capability>/`, `docs/adr/`, and `docs/research/`. Old `docs/prd/**` is **not indexed or treated as current product authority**. Copy valuable authored text to the correct current document, review its adoption status, fix references in active Tasks/Knowledge/Workflows, then delete the obsolete path only with the adopter's approval. Avoid empty scaffolding and shadow copies. Do not overwrite adopter-authored `AGENTS.md`, Workflows, `docs/PRD.md`, README files, `.gitignore` or local tool configuration automatically. The v0.14.1 manifest classifies local entry docs/settings as create-only; review existing content and reconcile with local policy first.

## 5. Refresh derived evidence and inspect the first task

```bash
./scripts/repoctl check --json
./scripts/repoctl meta check --json
./scripts/repoctl graph build --repo-id main --rebuild --json
./scripts/repoctl graph search 'next implementation and tests' --repo-id main --json
./scripts/repoctl graph workflow --symbol <known-symbol> --repo-id main --json
./scripts/repoctl task resume T-YYYYMMDDHHMMSSZ --json
```

The optional Tree-sitter structural adapter resolves syntax-level relations for Rust, Go, Java/Kotlin, Swift when installed. It does not prove type-dispatched or all cross-file calls. Inspect candidate and confirmed relationships separately and never treat missing tests as zero impact. The old `context` command and `context pack` are **removed**, not legacy aliases; update scripts to `graph search`, `graph query` or `knowledge query` based on their actual data needs.

## Rollback / stopping conditions

Before apply, keep a trusted adopter-specific backup of root docs, original Task/Knowledge files, ignored `.repoctl-state` and the root Git revision. If upgrade fails, restore the root control-plane **and** its matching task/receipt/Knowledge state together from that snapshot; do not restore only the Markdown while keeping later receipts/projections. Product repositories remain separate Git roots and should never be reset as a side-effect. If a per-ID Task/Knowledge conversion reports a conflict, preserve its original backup/witness for audit and stop. After restoration, rebuild only derived Graph/search and Knowledge projections from the restored source. v0.14 uses evidence-index schema 9, so an older schema 8 derived SQLite index is not a supported normal read source; rebuild before treating the new index as current. Release `v0.13.0` must not be reused as the transition target.

### Verify a stale Graph refresh only in an owner-approved target

In an already backed-up adopter workspace, a deliberately stale Graph can be inspected with read-only `graph workflow`; the owner may then run `graph workflow-benchmark --case-id <case> --fixture <path> --repo-id <id> --verify-refresh --json`. **This flag rebuilds the selected workspace's derived Graph cache**, not the product source. Its `refresh.source_rechecked` proof is valid only when a previously admitted stale source becomes current with a different validated Graph digest. A missing Dart compiler or unresolved cross-crate test remains partial, never invented as confirmed. Do not use the flag to modify adopter caches during template-source-only audits; use an isolated copy instead.
